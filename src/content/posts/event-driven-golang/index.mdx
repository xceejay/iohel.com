I built this project to understand event-driven architecture in practice, not in diagrams. I wanted to see events move, fail, retry, and recover in a real system I could run on my laptop.

The result is a small event-driven job engine in Go. This post is a walkthrough of how it works and what I learned from wiring it together.

## The core idea: jobs as events with a lifecycle

Most apps grow background jobs like weeds:

- one queue for emails
- another for payouts
- a cron script that flips flags
- a random table for retries

Every new case adds another special path.

Instead, this engine treats each job as an **event** that moves through a lifecycle. The lifecycle I ended up with looks like this:

- awaiting processing
- dispatched
- being processed
- succeeded
- failed (with retry rules)
- suspended
- expired

Everything the engine does is just safe movement between these states.

## Running the engine and UI

The repo lives at:

- `https://github.com/xceejay/event-driven-golang`

Once you have Go, MySQL, Redis, and NATS running, you can start the engine with:

```bash
make engine
```

and open the UI:

```bash
open http://localhost:8080
```

You will see a simple interface that lists events, their state, and how they move over time.

![Event engine UI](./meta.jpg)

The UI connects to the engine over SSE and WebSocket. It is not a full admin console. It is a visual debugger for how the lifecycle behaves.

## Architecture at a glance

The engine has four main parts:

1. **MCP server** that exposes tools and resources
2. **Event lifecycle service** that owns the state machine
3. **Repositories** for events, payloads, and configuration
4. **Dispatcher and scheduled jobs** that keep things moving

### MCP tools and resources

The MCP server defines tools like:

- `publish`
- `acquire_permit`
- `report_success`
- `report_failed`
- `suspend`
- `unsuspend`

and resources such as:

- a single event by ID
- pending events for a flow
- configuration for an event type
- simple queue metrics

That lets AI agents or other MCP clients drive the engine without talking directly to the database or NATS.

### Persistence and queues

The engine stores:

- events and configuration in **MySQL**
- payloads in **Redis** (or an in-memory map in development)
- metrics in memory and **Prometheus**

**NATS** sits on the edge as the message broker. When an event is ready to be processed, the dispatcher publishes it to a NATS subject for the relevant flow. An adapter subscribes, acquires a permit from the engine, does the work, then calls back with success or failure.

I chose NATS because it is small, fast, and fits Go well. It also has per message TTL headers built in, which is useful when you do not want old messages hanging around.

## Scheduled jobs as simple goroutines

Scheduling is handled by a few tight loops in goroutines instead of an external cron system. Each job is just a `time.Ticker` wrapped around repository calls and lifecycle transitions.

There are jobs for:

- pulling events that are awaiting processing per flow
- firing scheduled events when they become due
- expiring suspended events that have sat too long
- measuring queue sizes for metrics

Keeping this logic inside the engine makes it easier to reason about than a mix of crontabs and scripts.

## What I learned

A few practical lessons from building this:

- **A clear lifecycle beats scattered flags.** Once the states were defined, adding new behaviour (like suspension) meant adding transitions, not new boolean fields.
- **NATS is a good fit for small Go projects.** It kept the broker part simple so I could focus on the engine.
- **Goroutines and tickers are enough for many “cron” problems.** You do not always need a full scheduler library.
- **A tiny UI helps.** Seeing events flow in real time caught bugs that logs alone would have hidden.

## What is next

Right now the engine handles:

- basic event lifecycles
- configurable retries and backoff
- suspensions and expiry
- MCP integration for agents
- a small live UI

If I keep working on it, I want to explore:

- more flexible flow definitions
- better replay and audit tooling
- richer metrics and dashboards
- pluggable persistence backends

If you work with background jobs and you are tired of one off queues and scripts, this engine might be useful as a reference or a starting point, even if you never use it in production.
